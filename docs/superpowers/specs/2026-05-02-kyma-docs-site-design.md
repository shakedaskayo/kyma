# kyma Docs Site — Design

**Status:** draft for review
**Date:** 2026-05-02
**Owner:** kyma core
**Related:** [`2026-05-02-multi-source-database-integration-design.md`](2026-05-02-multi-source-database-integration-design.md)

---

## 1. Summary

kyma needs a public, end-to-end documentation site that covers every user-facing surface of the engine — ingest, query, connectors (including the just-specced multi-source database integration), agent endpoint, CLI, configuration, architecture — at a polish level matching the agentcy docs site. Today the only docs are `docs/architecture.md` and `docs/benchmarks.md`, plus internal specs under `docs/superpowers/`. This is insufficient for an engine that sells itself to agents and operators on understandability.

The site reuses the agentcy docs stack (VitePress 1.6, Vue 3, `vitepress-plugin-mermaid`, `markdown-it-attrs`, two-stage Dockerfile, Railway deploy) so we inherit a known-good build pipeline and visual identity rather than rebuilding one.

The site lives in-repo at `docs/site/` so docs change in the same PR as the code they describe. The existing `docs/architecture.md` and `docs/benchmarks.md` are pulled into the site (not duplicated). The `docs/superpowers/` subdir stays excluded from the build.

The non-trivial design choice is **how docs stay accurate** as kyma evolves. Two commitments:

1. **Mechanical reference content is autogenerated** from source-of-truth Rust code (HTTP routes, CLI commands, env vars, schema-mapping tables, connector capability matrices). The build fails if generated content is stale.
2. **Runnable KQL/SQL examples are doctested** — every `kql-runnable` / `sql-runnable` code block is executed against a real kyma instance in CI, snapshots compared. The build fails on drift.

Together, these mean the docs cannot lie about kyma's behavior — the same posture kyma's existing architecture takes toward correctness via property tests and architectural tests.

## 2. Goals & non-goals

### Goals

- One end-to-end documentation site covering every user-facing kyma surface: quickstart, concepts, ingest, query, connectors, reference, architecture, recipes.
- Visual and structural identity that matches agentcy docs, with a kyma-specific brand layer (color tokens, hero treatment, landing component).
- The site lives in-repo, in the same PRs as code changes.
- Reference content (HTTP API, CLI, env vars, type tables, capability matrices) is **autogenerated from Rust source** and the build fails on drift.
- **Runnable code examples are doctested** in CI against a real kyma instance.
- Mermaid diagrams in markdown + custom SVGs in `public/diagrams/` validated at build time (mirrors agentcy's `check-diagrams.mjs`).
- A queryable schema for the docs themselves: `llms.txt` exposes the full page index in a format kyma's own agent (and others) can use to answer "where do I read about X?"
- Custom domain (`docs.kyma.<domain>`) live from day one; canonical URLs in OG tags and search.
- Search built in via VitePress local search (no external service for v1).
- Dark / light mode work end-to-end, including Mermaid diagrams.

### Non-goals (v1)

- Versioned docs (`/v1`, `/v2`). The engine is at 0.0.1 — versioning is post-1.0.
- Internationalization. English-only.
- Authenticated / private docs sections. The site is fully public.
- A CMS for non-engineers to edit content. Authoring is markdown in PRs.
- Per-page edit-with-AI / "ask the docs" widget. Out of scope for v1; the agent endpoint covers the use case via `llms.txt`.
- Generated SDK reference (rustdoc, language clients). v1 is HTTP/CLI/KQL/SQL surfaces only. Rustdoc is a separate site at `docs.rs/kyma-*`.
- Doctests for the `/v1/agent/ask` endpoint — agent responses are non-deterministic by design. Agent docs are narrative + screenshots until determinism story changes.

## 4. Information architecture

### 4.1 Top-level sections

Eight, in order of user journey:

1. **Quickstart** (3–5 pages) — five-minute path: `docker compose up`, send one OTLP log, run one KQL query, see one result. Then a slightly longer "first real run" page that walks REST ingest + KQL + the web UI.
2. **Concepts** (8–12 pages) — what kyma is, the pruning cascade, extents and snapshots, the schema model (including `dynamic` and `vector(N)`), the agent loop, the five invariants, multi-source data (the new feature), retention and compaction, observability.
3. **Ingest** — REST/NDJSON, OTLP gRPC, Kafka, file-drop. One page per source. Plus shared pages: idempotency, JSON→Arrow coercion, schema evolution.
4. **Query** — KQL (with full language reference), SQL (DataFusion subset documented), PromQL (when ready), Arrow Flight, agent endpoint. Plus shared: pruning & performance, query budgets, limits.
5. **Connectors** — framework overview, Prometheus reference, Postgres / MySQL / Mongo (when shipped — gated behind milestone), federation vs. sync, the multi-source story including `live(table)`, `pushdown_summary`, `kyma_connector_health`. **This is the marquee section** for the engine going forward.
6. **Reference** (mostly autogenerated) — HTTP API, CLI, env vars, error codes, type tables, KQL function index, connector capability matrices.
7. **Architecture** — pulls in `docs/architecture.md` + `docs/benchmarks.md`; deeper than concepts; for contributors and platform builders.
8. **Recipes** — worked examples with copy-pasteable queries. Each follows one template (problem → schema → query → expected output → variations). Recipes only land *after* the underlying feature is documented in sections 1–7. v1 ships with at least three: "debug a prod incident across services," "join Postgres customers with kyma logs," "agent that watches CI failures."

### 4.2 Sidebar wiring

Exactly mirrors the agentcy pattern in `.vitepress/config.ts`: sidebar is a typed array of `{ text, items: [{ text, link }] }` groups, one per top section. Connectors uses `collapsed: false` so the catalog is expanded by default. Recipes is dynamically populated from `recipes.ts` (mirrors the agentcy use-cases pattern).

### 4.3 Naming conventions

- Hyphenated slugs (`docker-compose`, `pruning-cascade`, `live-vs-synced`).
- Title-case page titles in frontmatter.
- Absolute paths in links (`/concepts/pruning-cascade`).
- Reference pages slugged after the surface they document (`/reference/api/v1-query`, `/reference/cli/create-table`, `/reference/env/kyma-otlp-addr`).

### 4.4 Page templates

Three reusable patterns, each with required frontmatter:

```yaml
# Concept page (narrative, learning-oriented)
---
title: The pruning cascade
description: How kyma skips 99% of data on 99% of queries.
outline: deep
---

# How-to / ingest / query page (task-oriented)
---
title: Send OTLP logs to kyma
description: Configure your OTLP collector to ship to /v1/otlp.
---

# Reference page (lookup-oriented; mostly generated)
---
title: HTTP API — POST /v1/query
description: Run a KQL or SQL query against kyma.
sidebar: false   # generated pages skip sidebar; routed by parent index
---
<ApiEndpoint route="POST /v1/query" />
```

The landing (`index.md`) follows agentcy's `layout: page, sidebar: false, aside: false` pattern with `<Landing />`.

### 4.5 Recipe template (mirrors agentcy's recipe pattern)

```markdown
---
title: Debug a prod incident across services
description: Trace a single error across logs and traces in 3 KQL queries.
recipe:
  status: shipped
  difficulty: starter

[one paragraph]

## 5. Generated reference content (the anti-drift mechanism)

### 5.1 What's generated

Six JSON files under `docs/site/.vitepress/data/generated/`:

| File | Source of truth | Generator |
|---|---|---|
| `api-routes.json` | `kyma-server` axum route definitions + handler doc comments | `kyma-cli docs-export api` walks the router |
| `cli-commands.json` | `kyma-cli` `clap` definitions | `kyma-cli docs-export cli` introspects clap derive |
| `env-vars.json` | A new consolidated `KymaEnv` struct in `kyma-bin` | `kyma-cli docs-export env` reads its derive macro |
| `kql-functions.json` | `kyma-kql` parser registry + scalar UDF registry | `kyma-cli docs-export kql` walks the registry |
| `pushdown-capabilities.json` | Each `ExternalSource::capabilities()` (per the DB-integration spec) | `kyma-cli docs-export capabilities` |
| `schema-mappings.json` | `const TYPE_MAP` arrays in each engine impl (per the DB-integration spec) | `kyma-cli docs-export schema-mappings` |

Each generator is a sub-subcommand of `kyma-cli docs-export`, runs against compiled-in metadata only (no live kyma needed), and writes deterministic JSON.

### 5.2 The drift gate

`scripts/verify-generated.mjs` runs in CI after the `generated` job has written fresh JSON:

```
git diff --exit-code docs/site/.vitepress/data/generated
```

If a PR changes a route, flag, env var, KQL function, or schema mapping without regenerating, CI fails with a clear message: "run `cargo run -p kyma-cli -- docs-export` and commit the result." The same pattern as kyma's other gating tests.

### 5.3 Rendering

Vue components (`ApiEndpoint.vue`, `CliCommand.vue`, `EnvVarTable.vue`, `PushdownMatrix.vue`, `SchemaMappingTable.vue`) consume the JSON and render structured docs. Each component has one job and is < 200 lines. Hand-written narrative pages embed them inline:

```markdown
## Authentication

All endpoints accept a bearer token via `Authorization: Bearer <token>`.
Tokens are configured via `KYMA_AUTH_TOKENS` (space-separated).

<ApiEndpoint route="POST /v1/query" />

The `Content-Type` header selects the query language...
```

### 5.4 Failure modes

| Drift case | Detection | Resolution |
|---|---|---|
| New route added; generator not re-run | `verify-generated` fails | "run docs-export" |
| Route signature changed; doc comment stale | Generator captures fresh comments; site renders new ones | Auto-resolved (the doc comment is the source of truth) |
| Env var added without doc string | `KymaEnv` derive macro requires `#[doc = "..."]`; compile fails | Add the doc string |
| Generator itself broken | `cargo build` fails | Bug; team fixes |
| Generated JSON committed but Rust doesn't compile | `cargo build` fails before generator runs | Bug; team fixes |

The whole point: **the only path to documenting a new surface is via the source code**. Hand-written narrative explains *why*; generated reference shows *what*.

## 6. Doctests for runnable code blocks

### 6.1 Tagged code blocks

Markdown code blocks tagged with one of two languages are doctest-runnable:

````
```kql-runnable
otel_logs
| where severity_text == "ERROR"
| summarize n = count() by service_name
```

```sql-runnable
SELECT service_name, COUNT(*) FROM otel_logs
WHERE severity_text = 'ERROR' GROUP BY service_name
```
````

Untagged blocks (`kql`, `sql`, `bash`, `rust`) are syntax-highlighted but not executed. The author opts in by changing the language tag.

### 6.2 The `kyma-doctest` crate

A new private dev crate under `crates/kyma-doctest/`. Responsibilities:

1. Parse markdown files; extract `kql-runnable` and `sql-runnable` blocks with their position (file + line).
2. For each block: execute against a kyma instance pointed at by `KYMA_DOCTEST_URL` (default `http://localhost:8080`).
3. Compute a deterministic Arrow-result fingerprint: schema + sorted-by-all-columns row hash.
4. Compare against committed snapshot at `docs/site/.vitepress/generated/doctest-snapshots/<file-hash>/<block-index>.snap`.
5. On `--update-snapshots`: write fresh snapshots.
6. On normal run: assert clean diff; print failing block + expected/actual diff if not.

### 6.3 Test data

Doctests run against a kyma instance pre-loaded with a deterministic dataset. The dataset lives in `docs/site/doctest/seed/` as NDJSON files, one per table:

- `otel_logs.ndjson` — 10,000 synthetic OTLP log rows covering INFO/WARN/ERROR across 5 service names.
- `traces.ndjson` — 1,000 synthetic spans.
- `metrics.ndjson` — 5,000 synthetic metric points.
- `users.ndjson` — 100 rows for cross-source recipes (the row gets ingested as a kyma table; the connector-backed recipes mock the external source separately).

The dataset is committed (it's small, deterministic, and queries reference its specific values). Bumping the dataset is a deliberate PR.

### 6.4 docker-compose for doctests

`docs/site/doctest/compose.yml` mirrors the existing kyma `docker-compose.yml` but stripped down: Postgres, MinIO, kyma. No Kafka, no agent embeddings. Faster bring-up. Used by both local dev and CI.

```yaml
services:
  postgres:
    image: pgvector/pgvector:pg16
    ...
  minio:
    image: minio/minio:latest
    ...
  kyma:
    build: ../../..   # repo root
    depends_on: [postgres, minio]
    ports: ["8080:8080"]
    environment:
      KYMA_CATALOG_URL: postgres://kyma:kyma_dev@postgres:5432/kyma
      ...
```

### 6.5 Snapshot format

A snapshot is one YAML-formatted file per runnable block (`.snap` extension; YAML chosen for human-readable diffs in PR review):

```
schema:
  service_name: Utf8
  n: Int64
rows: 5
sorted_by_all_columns_blake3: 7a3b9c...
sample_rows:
  - {service_name: "auth-svc", n: 234}
  - {service_name: "payments-svc", n: 198}
  - {service_name: "search-svc", n: 412}
  - {service_name: "users-svc", n: 89}
  - {service_name: "web-svc", n: 156}
```

The hash is the assertion (deterministic, exact). The sample rows are for diff readability when the assertion fails.

### 6.6 Local UX

```sh
# Run all doctests against a local kyma:
cargo run -p kyma-doctest

# Update snapshots after an intentional behavior change:
cargo run -p kyma-doctest -- --update-snapshots

# Run only a specific file:
cargo run -p kyma-doctest -- docs/site/query/kql.md
```

### 6.7 Out of doctest scope (v1)

- `/v1/agent/ask` — non-deterministic by design.
- Time-windowed queries that depend on wall-clock (e.g., `ago(1h)` against a non-frozen dataset). The seed dataset uses a fixed `_timestamp` range; doctest examples use bounded ranges only.
- Cross-source queries against external DBs (covered in M3+ of the DB-integration spec).
- Performance assertions (latency / throughput). Those live in the existing `criterion` benches.

## 7. `llms.txt` for LLM legibility

### 7.1 What and why

`llms.txt` is an emerging convention for making documentation sites first-class consumers for LLMs. A flat plaintext index at the site root, one entry per page, with title + URL + description. Cheap, structured, parseable.

For kyma specifically: the `/v1/agent/ask` endpoint can preload `llms.txt` as a directory and answer "where do I read about X?" with a clickable link. Other agents (Cursor, ChatGPT, Claude) doing the same.

### 7.2 Generation

`scripts/gen-llms-txt.mjs` walks the VitePress site map after build:

```
# kyma docs

> Production knowledge, as a query.

## Quickstart
- [Five-minute start](https://docs.kyma.<domain>/quickstart/five-minute-start): docker compose up to first query
- [First real run](https://docs.kyma.<domain>/quickstart/first-run): ...

## Concepts
- [The pruning cascade](https://docs.kyma.<domain>/concepts/pruning-cascade): How kyma skips 99% of data on 99% of queries.
- [Extents and snapshots](https://docs.kyma.<domain>/concepts/extents-and-snapshots): The append-only storage model.
...
```

Format follows the [llms.txt convention](https://llmstxt.org/): markdown with H2 sections grouping pages, each entry as `- [title](url): description`.

### 7.3 Always at root

The generator writes `docs/site/public/llms.txt`, served at `/llms.txt`. Build fails if it's missing.

### 8.2 Reused CSS utilities (structure only; values change)

- `.arch-diagram` — bordered, rounded, scrollable container for SVG diagrams.
- `.feature-grid` — auto-fit 3-column card grid.
- `.feature-card` — soft background with hover.
- `.connector-grid` — auto-fill connector items.
- `.download-btn` — CTA buttons.

### 8.3 Landing page

`index.md` uses `<Landing />`, which must include:

- One-sentence value prop ("Production knowledge, as a query.").
- Hero diagram (the existing `docs/images/fan-in.svg` is a candidate; needs to be relocated to `docs/site/public/diagrams/`).
- A code sample that's actually runnable in the playground (or a static example).
- Featured recipes (3 cards).
- "What kyma is" / "How it works" / "An agent's trip through kyma" sections — the current README structure ports cleanly.

### 8.4 Diagrams

Two kinds:

- **Mermaid in markdown** — fenced ` ```mermaid ` blocks; theme configured via `vitepress-plugin-mermaid` in `config.ts`. Used for sequence diagrams, simple flowcharts.
- **SVG in `public/diagrams/`** — for architecture diagrams that need precise layout. Referenced via `<Diagram name="pruning-cascade" caption="..." />`. Validated at build time by `check-diagrams.mjs` (any reference must resolve to a real SVG; any `<image href="/icons/..."/>` inside an SVG must point to a real icon).

The existing diagrams in `docs/images/` (`fan-in.svg`, `architecture.svg`, `agent-query-lifecycle.svg`) port over to `docs/site/public/diagrams/`.

### 8.5 Code-block treatment

VitePress defaults are good. Two additions:

- Lines tagged `kql-runnable` / `sql-runnable` get a small "runnable" badge in the upper-right of the block, linking to a future playground (post-v1) or just visually distinguishing runnable from illustrative.
- Long results from generated examples are auto-collapsible (`<details>` with the first 5 rows visible).

### 9.2 Custom domain

`docs.kyma.<domain>` configured on the Railway service from day one (the exact domain is named at D0 — see §12, question 1). All canonical URLs in OG metadata, sitemap, and `llms.txt` use this domain.

### 9.3 Why not GitHub Pages / Cloudflare Pages / Vercel

Doctests in CI need a Docker-in-Docker host. Pages/Cloudflare/Vercel build runners don't support that; they're static-site builders. Doctests therefore run in GitHub Actions (which we already use), produce committed snapshots, and the deploy host just renders. Railway is the right deploy host because:

1. It matches the existing kyma engine deploy pattern (one Railway account, two services).
2. It matches the agentcy docs deploy pattern (the team already operates this).
3. If docs ever need auth, Railway supports it; Pages does not natively.

The cost difference vs. Pages is negligible at docs traffic levels.

### 9.4 Watching for rebuild

Railway's `watchPatterns` triggers a rebuild on any change to `docs/site/`, `docs/architecture.md`, `docs/benchmarks.md`, or `docs/images/`. Code changes elsewhere don't redeploy docs. The doctest CI job runs on the same triggers but in Actions, so a code change that breaks a documented behavior fails the *doctest* job before merging — meaning the docs only ever deploy after their assertions pass.

### 11.2 Connector-section gating

The Connectors section is **co-shipped with the DB-integration milestones**:

- Connectors framework + Prometheus reference page lands in **D1** (existing surface).
- Postgres connector pages land when M1 of the DB integration ships.
- MySQL connector pages land at M2.
- Mongo connector pages land at M3.
- The "Multi-source data" marquee page lands at M1 with the federation+sync explainer, `live(table)`, `pushdown_summary`, `kyma_connector_health`.

Each engine page uses `<PushdownMatrix>` and `<SchemaMappingTable>` rendered from the JSON generated by the corresponding `ExternalSource` impl. So the connector docs are *born* drift-proof: shipping a new engine impl means generating its capability + mapping JSON, which the docs site picks up automatically.

## 12. Open questions for D0 review

1. **Exact domain.** `docs.kyma.<what>`? Likely `docs.kyma.agentcylabs.com` if kyma is positioned as an Agentcy product, or a standalone domain if it's marketed independently. Resolve before D0 deploy so the OG / sitemap / llms.txt URLs are stable.
2. **Brand palette.** Defer to a design pass; the structural CSS tokens are committed in this design but the values aren't. D0 ships with a placeholder palette; D4 polishes it.
3. **README ↔ landing page.** The current `README.md` has strong narrative content ("kyma fan-in", "What kyma is", "How it works", "An agent's trip through kyma"). The landing should incorporate it. Decision at D0: do we *replace* sections of `README.md` with links to the docs site, or keep `README.md` standalone? Recommendation: keep README as the GitHub-discoverable summary (capped at one screen), and the docs site is the canonical long-form home.
4. **pnpm vs. npm.** kyma's root uses pnpm (`pnpm-workspace.yaml`, `pnpm-lock.yaml`); agentcy docs use npm. Recommendation: align with the kyma root (pnpm) for consistency; the Dockerfile and scripts adjust to `pnpm`. Trivial change.
